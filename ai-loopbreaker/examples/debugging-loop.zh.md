# 案例：打断反复打补丁的循环

**中文** | [English](debugging-loop.md)

## 未使用 LoopBreaker

```text
用户：调整超时之后，认证集成测试还是失败。

助手：问题可能在 mock 时钟。我来改一下 mock。

用户：还是失败。

助手：可能需要把 mock 延迟调得更大。我再增加一次。

用户：堆栈没有变化。

助手：真正的问题可能是测试运行器配置。我来重写测试初始化，
      并更新共享测试框架。
```

这段对话看起来在推进，因为每一轮都有新诊断和新补丁。但实际上，根因从未被观察。堆栈没有变化，补丁数量在增加，范围也在扩大。

## 使用 LoopBreaker

```text
循环：LB-04 修复打转
重复：两次 mock 时序修改都针对同一个测试，而堆栈中的首个失败边界没有变化。
新证据：超时修改没有移动失败位置。
根因未知：认证请求是否真正到达 token exchange。
下一动作：运行最小失败用例，记录请求和 token exchange 日志，
         定位第一次状态偏离预期的位置。
完成条件：最小认证用例通过，且现有集成测试不回归。
需要决策：无。
```

第二个回答没有立刻修好 bug，但它把工作从推测性打补丁改成了观察执行边界，这才是真正的推进。

## 为什么有效

- 明确指出重复失败；
- 区分“增加投入”和“产生新证据”；
- 拒绝用大范围重写逃避诊断；
- 下一动作小、可观察，并且能改变假设；
- 在尝试下一个补丁前定义完成条件。
