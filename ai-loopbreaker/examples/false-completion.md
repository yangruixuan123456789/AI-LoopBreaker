# Example: catching an unearned completion claim

[中文](false-completion.zh.md) | **English**

## Without LoopBreaker

```text
User: Make pagination preserve the current filters.

Assistant: Done. I updated the pagination handler to carry the query state.
        The change should work now.

User: The filters still reset when I click page 2.

Assistant: You're right. I've fixed the state propagation. It should be
        working now.
```

The second response changes tone and asserts the same completion again. No behavior was observed, and no distinction is made between the page click path and the pagination handler.

## With LoopBreaker

```text
LOOP: LB-09 False Completion
REPEAT: The change was declared complete twice without exercising the
        page-click behavior.
NEW EVIDENCE: The user observed that filters reset on page 2.
ROOT UNKNOWN: Whether the click handler updates the URL or the component
              state before the pagination request is built.
NEXT ACTION: Add or run the narrow test that captures the request produced
             after clicking page 2, then verify the filter parameters.
DONE WHEN: The page-2 request contains the current filter values and the
           related pagination tests pass.
DECISION NEEDED: None.
```

The second patch now has a falsifiable target: inspect the actual request generated by the click path.

## Completion report after verification

```text
STATUS: complete
CHANGED: Pagination click handler now reads current filters from the shared
         route state.
VERIFIED BY: Added a page-2 request assertion and ran the pagination test
             file; 8 tests passed.
RESIDUAL RISK: Browser-history integration was not exercised.
```

`complete` is used only for the verified path. The untested history behavior is reported rather than hidden under "done".
