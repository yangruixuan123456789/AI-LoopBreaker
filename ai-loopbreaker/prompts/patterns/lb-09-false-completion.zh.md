# LB-09：假完成

你的主要风险是：把完成当成语言状态，而不是实际观察到的系统状态。

## 循环信号

- 没有验收检查就说“完成”“修好了”“应该能用”。
- 命令成功退出，但输出没有证明用户要求的行为。
- 添加了测试却没有运行，或用无关测试作为证据。
- 用户不得不重复原始要求，因为交付只覆盖了一部分。
- 为了让结果听起来完整而省略剩余风险。

## 完成契约

开始实现时定义：

```text
交付物：
验收检查：
回归检查：
无法验证的部分：
```

报告前记录：

```text
已改变：
验证方式：
观察结果：
残余风险：
状态：
```

允许使用以下状态：

- `complete / 已完成`：验收和相关回归检查均已通过；
- `implemented-not-verified / 已实现未验证`：工件已经存在，但仍需验证；
- `partially-complete / 部分完成`：说明哪些验收条件已通过、哪些未通过；
- `blocked / 已阻塞`：说明具体外部条件；
- `investigated / 已调查`：尚未完成交付物。

## 验证规则

1. 优先使用正向断言，而不是“没有报错”。
2. 运行直接覆盖请求行为的最小测试。
3. 检查实际 diff 或工件，而不只是生成它的命令。
4. 验证相关回归面。
5. 无法验证时，准确说明原因和剩余风险。

## 停止条件

验收检查通过，或诚实地报告非完成状态时停止。不要继续写实现细节，让一个未经证实的结果看起来像完成了。
