# LB-13：修复覆盖不全

你的主要风险是：把 BUG 定位到第一个报错行，让报告中的症状消失，然后宣布这一类 BUG 已经关闭；但同一个不变量在相邻入口、状态或调用方中仍然是坏的。

这与 `LB-04 修复打转`不同。LB-04 处理的是反复补丁仍然无法解决同一个失败；这里第一个补丁在局部生效，但修复并不完整。

## 循环信号

- 只修改堆栈或报错直接指向的那一行。
- 测试只覆盖用户提供的例子，没有覆盖它背后的不变量。
- 相似的处理器、路由、任务、适配器、查询或校验路径没有处理，也没有解释。
- 在症状表面增加特例，而不是在共享的决策边界修正规则。
- 一种角色、状态、平台或输入形式通过，却没有检查对应分支。
- 用“原来的报错没了”推断成功，而不是用行为一致性证明成功。

## 1. 定义 BUG 类别

修改前说明：

```text
报告症状：
被破坏的不变量：<不依赖某个代码位置的必须始终成立条件>
触发条件：
需要保持的一致性：
```

例如：

```text
报告症状：点击第 2 页后筛选条件重置。
被破坏的不变量：分页必须在所有导航路径中保留完整有效的查询条件。
触发条件：应用筛选后发生任意页面切换。
需要保持的一致性：首页、下一页、上一页、直接跳页和历史导航产生等价的请求。
```

如果你无法说明不变量，就还没有界定 BUG 类别。

## 2. 绘制影响面

不要只搜索失败文件。寻找所有表达或依赖同一不变量的位置，根据代码库选择合适证据：

- 调用方与被调用方；
- 重复或平行实现；
- 路由、页面、命令和事件处理器；
- 状态转换和导航路径；
- 后台任务、队列、重试、取消和超时；
- 适配器、序列化、校验、规范化和持久化；
- 权限、角色、租户、语言和功能开关；
- 缓存及其失效路径；
- 数据迁移和旧数据兼容；
- 集成测试与契约边界；
- 描述旧行为或新行为的测试。

除了搜索概念，也要搜索具体符号：错误文本、路由名、函数名、状态枚举、查询谓词和重复字面量，常常能暴露平行路径。

## 3. 选择正确的修复位置

选择能够一致执行该不变量的最窄边界。

以下情况优先修正共享决策边界：

- 多个入口必须遵守同一条规则；
- 复制修复会导致未来行为分叉；
- 不变量可以在一处表达，且不会耦合无关行为。

以下情况使用局部修复：

- 只有一条路径真正拥有这个不变量；
- 集中处理会产生人为抽象或大范围副作用；
- 各路径本来就有明确不同的契约。

为每个受影响面记录一个结论：

```text
影响面：
路径或入口：
已修复 / 原本正确 / 有意不同 / 暂存
证据：
```

不要悄悄遗漏影响面。“有意不同”必须有理由。

## 4. 建立关闭矩阵

验证 BUG 类别，而不是只验证原始复现。根据风险选择检查：

```text
用例 | 输入/状态 | 预期不变量 | 验证方式 | 结果
```

按适用性考虑：

- 原始失败用例；
- 所有发现的相邻路径；
- 空值、缺失、格式错误和旧数据输入；
- 成功、错误、重试、超时、取消和恢复状态；
- 首页、末页、直接跳页和前进/后退行为；
- 至少一个相关集成或契约边界；
- 最近的回归面。

## 5. 同时守住修复范围和修改范围

不要：

- 为了让补丁通过而削弱或跳过有效测试；
- 捕获并吞掉错误，却没有真正执行不变量；
- 把同一修复复制到多条路径后，在没有测试的情况下假设它们一致；
- 因为影响搜索发现了问题，就顺手重构无关代码；
- 在没有证据要求时改变不变量之外的公共行为。

如果影响面中存在真正独立的另一个 BUG，把它暂存，并说明为什么不属于本次修复。

## 6. 完成条件

只有同时满足以下条件，修复才算完整：

1. 原始症状已经被复现，并在修复后通过；
2. 每个发现的影响面都已修复、原本正确，或有证据地明确排除；
3. 相关的调用路径和状态变体通过；
4. 测试断言的是不变量，而不只是旧实现细节；
5. 最终报告说明修复边界和仍存在的影响面。

报告：

```text
BUG 类别：
根因修复位置：
已检查影响面：
已验证用例：
有意未修改：
残余风险：
```

如果唯一证据只是“原来那一行不报错了”，不要报告 `complete / 已完成`。
